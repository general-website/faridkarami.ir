معرفی SurrealDB

اگر در دنیای Backend کار می کنید، احتمالا بارها با این معماری روبه رو شده اید: PostgreSQL برای داده های اصلی، Redis برای Cache و Elasticsearch برای Search و یک سرویس جدا برای Vector Search. هر کدام از این ابزارها کار خودشان را خوب انجام می دهند، اما اضافه شدن هر سرویس یعنی Configuration بیشتر، Monitoring بیشتر، Backup بیشتر و یک بخش دیگر از معماری که باید مدیریت شود.

SurrealDB با ایده متفاوتی وارد این فضا شده است: یک Database چندمدلی که بتواند داده های Relational، Document، Graph، Vector، Text و Time-Series را در یک Engine مدیریت کند. Query Language آن نیز SurrealQL است؛ زبانی شبیه SQL که قابلیت هایی مثل Record Link و Graph Traversal را به آن اضافه می کند.

در این مقاله از نگاه یک توسعه دهنده Backend بررسی می کنیم SurrealDB چیست، چرا مورد توجه قرار گرفته، چه تفاوتی با PostgreSQL و MongoDB دارد، چگونه با Node.js و NestJS از آن استفاده کنیم و چه زمانی انتخاب آن منطقی است.

SurrealDB چیست؟

SurrealDB یک Multi-model Database نوشته شده با Rust است. طبق مستندات رسمی، یک Engine می تواند داده های Relational، Document، Graph، Vector، Text، Time-Series و Geospatial را مدیریت کند.

اما Multi-model بودن در عمل یعنی چه؟ فرض کنید یک شبکه اجتماعی می سازیم. اطلاعات کاربر یک Document است:

{
	"name": "FaridKarami",
	"email": "faridkarami@example.com"
}

ارتباط کاربر با یک Post می تواند Graph باشد:

User -> writes -> Post

ارتباط کاربر با Company نیز می تواند به شکل Graph مدل شود:

User -> works_at -> Company

حالا اگر بخواهیم روی متن Post ها Search انجام دهیم یا برای Recommendation از Embedding استفاده کنیم، Vector و Full-text Search هم وارد معماری می شوند.

ایده SurrealDB این است که چنین مدل هایی بتوانند در یک Engine قرار بگیرند، به جای اینکه برای هر کدام Database جداگانه وارد پروژه کنیم.

چرا SurrealDB جالب است؟

جذابیت SurrealDB یک Feature منفرد نیست؛ ترکیب قابلیت هاست:

  • Document Data
  • Relational Data
  • Graph Relations
  • Vector Search
  • Full-text Search
  • Time-Series
  • Live Queries
  • Authentication و Permissions
  • Embedded Database
  • SDK برای زبان های مختلف

این قابلیت ها در مستندات رسمی SurrealDB به عنوان بخش هایی از یک Platform چندمدلی معرفی شده اند.

تفاوت SurrealDB با PostgreSQL و MongoDB

اولین سوال طبیعی این است: «اگر PostgreSQL و MongoDB داریم، چرا SurrealDB؟»

پاسخ به نوع پروژه بستگی دارد. PostgreSQL یک Database Relational بسیار بالغ با Ecosystem گسترده است و MongoDB برای مدل Document-oriented بسیار شناخته شده است. SurrealDB تلاش می کند Data Model های مختلف را در یک Engine ترکیب کند.

ویژگی PostgreSQL MongoDB SurrealDB
Relational بسیار قوی محدودتر دارد
Document JSON/JSONB بومی دارد
Graph امکانات جانبی محدودتر بومی
Record Link Foreign Key Reference بومی
Vector با امکانات مرتبط دارد دارد
Full-text دارد دارد دارد
Time-Series دارد دارد دارد
Live Query معمولا با ابزارهای جانبی Change Streams بومی
Embedded معمول نیست معمول نیست دارد
Query Language SQL Mongo Query SurrealQL
Ecosystem بسیار بالغ بسیار بالغ در حال رشد

این جدول رتبه بندی Database ها نیست. هدف آن نشان دادن تفاوت رویکردهاست.

SurrealQL چیست؟

SurrealQL زبان Query اصلی SurrealDB است. Syntax آن برای کسی که SQL می داند آشنا به نظر می رسد:

SELECT name, email
FROM user
WHERE age >= 18;

اما SurrealQL امکانات مخصوص SurrealDB را هم دارد؛ از جمله Record ID، Record Link و Graph Traversal.

مثلا:

SELECT
    name,
    ->writes->post AS posts
FROM user;

در همین Query علاوه بر اطلاعات User، از Graph به سمت Post هایی که نوشته شده اند حرکت می کنیم.

Record ID در SurrealDB

در Database های Relational معمولا یک ستون id داریم. در SurrealDB شناسه یک Record می تواند به شکل زیر باشد:

user:faridkarami

این مقدار هم نوع Record را مشخص می کند و هم ID آن را.

برای ساختن چنین Record ای:

CREATE user:faridkarami SET
    name = "FaridKarami",
    email = "faridkarami@example.com";

CRUD ساده

ایجاد:

CREATE user:faridkarami SET
    name = "FaridKarami",
    age = 35;

خواندن:

SELECT * FROM user;

یا یک Record مشخص:

SELECT * FROM user:faridkarami;

ویرایش:

UPDATE user:faridkarami SET
    age = 36;

حذف:

DELETE user:faridkarami;

اگر SQL بلد باشید، شروع کار بسیار سریع است.

Document Data

SurrealDB می تواند Object و Array های تو در تو را ذخیره کند:

CREATE user:faridkarami SET
    name = "FaridKarami",
    skills = ["Node.js", "TypeScript", "NestJS"],
    profile = {
        city: "Tehran",
        website: "https://example.com"
    };

البته PostgreSQL با JSONB نیز چنین سناریوهایی را پوشش می دهد؛ بنابراین Document بودن به تنهایی دلیل کافی برای انتخاب SurrealDB نیست. ارزش اصلی در ترکیب Document با سایر مدل هاست.

Schema؛ آزاد یا Strict؟

SurrealDB امکان تعریف Schema را فراهم می کند. برای یک پروژه Production می توان ساختار داده را صریح تعریف کرد:

DEFINE TABLE user SCHEMAFULL;

DEFINE FIELD name ON user TYPE string;
DEFINE FIELD email ON user TYPE string;
DEFINE FIELD age ON user TYPE int;

می توان Constraint نیز تعریف کرد:

DEFINE FIELD age ON user
    TYPE int
    ASSERT $value >= 0;

این کار بخشی از Data Integrity را در خود Database کنترل می کند.

Index ها

اگر Email را زیاد جستجو می کنیم، Index مناسب می سازیم:

DEFINE INDEX user_email
ON user
FIELDS email
UNIQUE;

Index بیش از حد نیز خوب نیست. هر Index Storage و هزینه Write بیشتری ایجاد می کند. بنابراین Index را بر اساس Query های واقعی طراحی کنید.

Relation؛ جایی که SurrealDB متفاوت می شود

فرض کنید User در یک Company کار می کند. در مدل Relational ممکن است سه بخش داشته باشیم:

user
company
user_company

در SurrealDB می توان Relation را مستقیما مدل کرد:

RELATE user:faridkarami->works_at->company:unixic;

مدل Data به شکل زیر خواهد بود:

user:faridkarami
     |
     | works_at
     v
company:unixic

Relation خودش Data دارد

Relation همیشه یک Link ساده نیست. مثلا می خواهیم سمت و تاریخ شروع کار را هم ذخیره کنیم:

RELATE user:faridkarami->works_at->company:unixic
SET
    position = "CTO",
    started_at = time::now();

حالا Relationship خودش Data دارد.

این مدل برای مواردی مثل موارد زیر طبیعی است:

User -> follows -> User
User -> works_at -> Company
User -> likes -> Post
User -> purchased -> Product
Student -> enrolled_in -> Course

Graph Traversal

یکی از جذاب ترین قابلیت های SurrealQL، حرکت روی Graph در همان Query است:

SELECT ->follows->user
FROM user:faridkarami;

یا یک مسیر طولانی تر:

SELECT ->follows->user->writes->post
FROM user:faridkarami;

این قابلیت باعث می شود Relationship بخشی از زبان Query باشد، نه فقط یک Foreign Key معمولی.

آیا SurrealDB یک Graph Database است؟

SurrealDB قابلیت Graph دارد، اما تعریف دقیق تر آن Multi-model Database است. می توانید در یک Application همزمان Document، Relation، Graph و Vector داشته باشید.

برای مثال در یک فروشگاه:

Product
   |
   +-- category
   |
   +-- embedding
   |
   +-- purchased_by -> Customer

استفاده از SurrealDB با Node.js

SDK رسمی JavaScript/TypeScript برای اتصال به SurrealDB وجود دارد.

نصب:

npm install surrealdb

اتصال:

import { Surreal } from 'surrealdb';

const db = new Surreal();

await db.connect('ws://localhost:8000', {
	namespace: 'company',
	database: 'production',
	authentication: {
		username: 'root',
		password: 'secret',
	},
});

اجرای Query:

const [users] = await db.query('SELECT * FROM user');

console.log(users);

SDK رسمی از HTTP و WebSocket و همچنین Embedded Engine ها پشتیبانی می کند.

Parameterized Query

در Backend واقعی، مقدار کاربر را با String Concatenation وارد Query نکنید.

روش نامناسب:

const query = `
    SELECT * FROM user
    WHERE email = '${email}'
`;

روش بهتر:

const [users] = await db.query(
	`
    SELECT * FROM user
    WHERE email = $email
    `,
	{ email },
);

این روش هم خواناتر است و هم برای جلوگیری از Query Injection مناسب است.

SurrealDB در NestJS

اگر با NestJS کار می کنید، بهتر است Connection را در یک Service مرکزی نگه دارید:

import { Injectable, OnModuleDestroy, OnModuleInit } from '@nestjs/common';
import { Surreal } from 'surrealdb';

@Injectable()
export class DatabaseService
	extends Surreal
	implements OnModuleInit, OnModuleDestroy
{
	async onModuleInit() {
		await this.connect(process.env.SURREAL_URL!, {
			namespace: process.env.SURREAL_NAMESPACE!,
			database: process.env.SURREAL_DATABASE!,
			authentication: {
				username: process.env.SURREAL_USERNAME!,
				password: process.env.SURREAL_PASSWORD!,
			},
		});
	}

	async onModuleDestroy() {
		await this.close();
	}
}

Live Query؛ وقتی Data خودش به سمت Client می آید

در Application های Real-time، روش سنتی Polling است:

Client -> GET every 5 seconds -> Backend -> Database

SurrealDB قابلیت Live Query دارد که تغییرات Data را به Subscriber ها منتقل می کند. این ویژگی برای Chat، Dashboard، Notification و سیستم های Collaborative می تواند مفید باشد.

البته برای یک CRUD معمولی، استفاده از Live Query لزوما ارزش معماری اضافه را ندارد.

Embedded Database

یکی از تفاوت های جالب SurrealDB امکان اجرای آن به صورت Embedded است.

در مستندات رسمی، JavaScript SDK برای Node.js، Bun و Deno یک Engine بومی ارائه می کند و WebAssembly نیز برای Browser قابل استفاده است. Storage هایی مانند mem://، rocksdb:// و surrealkv:// نیز برای Engine های مرتبط معرفی شده اند.

در نتیجه معماری می تواند به جای:

Application -> Remote Database

به شکل زیر باشد:

Application
    ↓
Embedded SurrealDB

این مدل برای بعضی Desktop، CLI، Local-first و Edge Application ها جذاب است.

SurrealDB 3.0 چه چیزی اضافه کرد؟

SurrealDB 3.0 یک Release مهم بود و قابلیت هایی مانند Streaming Query Planner، WASM Extensions، File Storage، In-memory Engine و تغییرات گسترده در Indexing و Query Execution را معرفی کرد.

در Release های 3.0 همچنین بهبودهایی برای Graph Execution و Vector Index وجود داشته است. این روند نشان می دهد SurrealDB در حال حرکت به سمت یک Data Platform چندمنظوره است.

آیا SurrealDB می تواند جای Redis را بگیرد؟

نه لزوما.

Redis معمولا برای مواردی مثل Cache، Session، Rate Limit، Queue و Pub/Sub استفاده می شود. SurrealDB هدف متفاوتی دارد.

ممکن است در یک پروژه برخی نیازهای Redis با معماری دیگری پوشش داده شوند، اما حذف Redis باید نتیجه نیاز واقعی پروژه باشد، نه صرفا وجود یک Feature مشابه.

آیا SurrealDB می تواند جای PostgreSQL را بگیرد؟

در بعضی پروژه ها ممکن است، اما پاسخ عمومی وجود ندارد.

اگر پروژه شما شدیدا به PostgreSQL Extension ها، ابزارهای BI، ORM های خاص یا Ecosystem PostgreSQL وابسته است، Migration می تواند پرهزینه باشد.

اگر پروژه جدیدی دارید که از ابتدا به Document، Graph، Realtime و Vector نیاز دارد، SurrealDB ارزش بررسی بیشتری پیدا می کند.

چه زمانی انتخاب SurrealDB منطقی نیست؟

گاهی انتخاب نکردن تکنولوژی جدید بهترین تصمیم فنی است.

اگر یک پروژه PostgreSQL موجود دارید که صدها Query، Extension، ORM، ابزار گزارش گیری و فرآیند عملیاتی آن بر پایه PostgreSQL ساخته شده، مهاجرت صرفا برای استفاده از یک Database جدید معمولا نیازمند تحلیل هزینه و ریسک است.

همچنین اگر تمام نیاز پروژه یک CRUD Relational ساده است و Database فعلی آن را به خوبی پوشش می دهد، اضافه کردن تکنولوژی جدید لزوما ارزش ایجاد نمی کند.

Ecosystem را جدی بگیرید

Database فقط Engine نیست.

هنگام انتخاب Database باید به این موارد هم نگاه کنید:

  • ORM و Migration Tools
  • Monitoring
  • Backup و Restore
  • Hosting
  • Community
  • نیروی متخصص
  • Documentation
  • Integration ها
  • ابزارهای BI
  • هزینه Migration آینده

SurrealDB نسبت به PostgreSQL و MongoDB جوان تر است و طبیعی است که Ecosystem کوچک تری داشته باشد. بنابراین انتخاب آن باید علاوه بر Feature ها، با توجه به شرایط تیم و محصول انجام شود.

Transaction

برای عملیات حساس، Transaction اهمیت زیادی دارد. مثلا انتقال وجه:

BEGIN TRANSACTION;

UPDATE account:alice
SET balance -= 100;

UPDATE account:bob
SET balance += 100;

COMMIT TRANSACTION;

در JavaScript SDK نیز Transaction ها پشتیبانی می شوند.

Security

وقتی Database وارد Production می شود، Feature ها کافی نیستند. باید به Authentication، Authorization، Permissions، TLS، Secrets، Network Isolation و Backup Security توجه شود.

SurrealDB قابلیت های مربوط به Authentication و Row-level Permissions دارد. در Backend نیز بهتر است Root Credentials را برای تمام عملیات Application استفاده نکنید.

Performance؛ Feature List کافی نیست

یکی از اشتباهات رایج این است که Database ها را با تعداد Feature مقایسه کنیم.

Production Checklist

قبل از Production موارد زیر را بررسی کنید:

  • Authentication فعال باشد
  • Root Credentials امن باشند
  • Application User جدا باشد
  • Database بدون دلیل روی Public Internet نباشد
  • TLS بررسی شده باشد
  • Backup فعال باشد
  • Restore واقعا تست شده باشد
  • Index ها بر اساس Query های واقعی باشند

  • Connection Lifecycle درست مدیریت شود
  • Monitoring و Logging داشته باشید
  • Storage Persistence تست شده باشد

SurrealDB تلاش می کند یک مشکل مهم معماری مدرن را حل کند: Data همیشه فقط یک جدول Relational ساده نیست.

یک Application ممکن است همزمان Document، Relation، Graph، Vector، Search و Real-time Data داشته باشد. SurrealDB این مدل ها را در یک Engine قرار می دهد و SurrealQL را برای کار با آنها ارائه می کند.

این رویکرد برای پروژه هایی که Domain پیچیده و Relationship-heavy دارند جذاب است. از طرف دیگر، PostgreSQL و MongoDB Ecosystem های بسیار بالغی دارند و صرفا جدید بودن SurrealDB دلیل کافی برای Migration نیست.

اگر بخواهیم رویکردها را خلاصه کنیم:

PostgreSQL
    ↓
Relational First

MongoDB
    ↓
Document First

SurrealDB
    ↓
Multi-model First

مهم ترین سوال قبل از انتخاب این نیست که «کدام Database بهتر است؟» بلکه این است که مدل داده و Workload پروژه من چیست و کدام ابزار با کمترین پیچیدگی نیاز واقعی من را پوشش می دهد؟
