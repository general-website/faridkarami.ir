1. Cell-Based Architecture چیست؟

Cell-Based Architecture یک الگوی طراحی برای سیستم های توزیع شده است که در آن کل Workload نرم افزار به چند واحد مستقل به نام Cell تقسیم می شود. هر Cell مسئول پردازش بخشی از درخواست ها یا کاربران است و تا حد امکان تمام اجزای لازم برای انجام کار خود را در اختیار دارد.

هر Cell را می توان یک نمونه عملیاتی مستقل از کل یا بخش اصلی سیستم در نظر گرفت. این نمونه معمولا شامل لایه اجرای برنامه، ذخیره سازی، Cache، پردازش های پس زمینه، تنظیمات عملیاتی و ابزارهای پایش است.

هدف اصلی فقط افزایش ظرفیت نیست؛ هدف مهم تر، محدود کردن محدوده اثر خرابی (Blast Radius) است. اگر یک Cell به دلیل Bug، بار بیش از حد، خطای Deployment یا مشکل زیرساختی از دسترس خارج شود، اختلال باید به درخواست ها و کاربران همان Cell محدود بماند و سایر Cellها بتوانند به کار ادامه دهند.

مثال ساده

فرض کنیم یک سرویس 100,000 کاربر دارد. به جای اینکه همه کاربران به یک مجموعه مشترک از Backend و Database وابسته باشند، کاربران میان 10 Cell تقسیم می شوند.

                         USERS
                           |
                     CELL ROUTER
                           |
          +----------------+----------------+
          |                |                |
        CELL 1           CELL 2           CELL 3
          |                |                |
      Application      Application      Application
      Database         Database         Database
      Cache            Cache            Cache
      Workers          Workers          Workers
          |                |                |
          +----------------+----------------+
                           |
                       ... CELL N

اگر Cell 2 دچار مشکل شود، کاربران اختصاص داده شده به Cell 2 ممکن است اختلال را تجربه کنند، اما کاربران Cellهای دیگر همچنان سرویس می گیرند.

این معماری تضمین نمی کند که هیچ خرابی سراسری رخ ندهد؛ بلکه طراحی می شود تا احتمال و دامنه چنین خرابی هایی کاهش یابد.

مفاهیم کلیدی

  • Cell: واحد مستقل اجرای Workload.
  • Cell Router: لایه سبک برای هدایت درخواست به Cell درست.
  • Partition Key: کلیدی که بر اساس آن کاربران یا درخواست ها تقسیم می شوند.
  • Control Plane: بخش مدیریتی برای ساخت، پیکربندی، انتقال و مدیریت Cellها.
  • Data Plane: بخشی که درخواست های اصلی کاربران را پردازش می کند.
  • Blast Radius: محدوده ای از سیستم که تحت تاثیر یک خرابی قرار می گیرد.
  • Cell Rebalancing: انتقال کنترل شده کاربران یا بار میان Cellها.
  • Cell Sizing: تعیین ظرفیت و اندازه مناسب هر Cell.

2. چرا به این معماری نیاز داریم؟

در معماری متمرکز، ممکن است چندین نسخه از Backend داشته باشیم، اما همه آن ها همچنان از Database، Queue یا منابع مشترک استفاده کنند. در چنین شرایطی افزایش تعداد سرورها لزوما محدوده خرابی را کوچک نمی کند.

برای نمونه:

  • افزایش ناگهانی ترافیک ممکن است Database مشترک را از کار بیندازد.
  • یک Migration اشتباه می تواند تمام کاربران را تحت تاثیر قرار دهد.
  • یک نسخه معیوب از برنامه ممکن است روی تمام Instanceها منتشر شود.
  • یک Tenant پرمصرف می تواند منابع سایر Tenantها را مصرف کند.
  • اختلال در یک سرویس مشترک می تواند چندین بخش ظاهرا مستقل را همزمان مختل کند.

Cell-Based Architecture تلاش می کند مرزهای خرابی را به واحدهای کوچک تر و قابل کنترل تبدیل کند.

Fault Isolation

هر Cell باید تا حد امکان منابع و داده های عملیاتی مستقل داشته باشد. استقلال صرفا به معنی اجرای چند Container جدا نیست. اگر تمام Containerها به یک Database مشترک و یک Queue بدون محدودیت وابسته باشند، آن منابع همچنان نقطه خرابی مشترک هستند.

Static Stability

یک Cell سالم باید بتواند بدون نیاز دائمی به هماهنگی با سایر Cellها، کارهای اصلی خود را انجام دهد. وابستگی های بین Cellها باید کم، مشخص و کنترل شده باشند.

مقیاس پذیری

وقتی ظرفیت یک Cell کافی نیست، می توان Cell دیگری ایجاد کرد و بخشی از کاربران یا Workload جدید را به آن اختصاص داد. این کار به جای بزرگ کردن بی حد و مرز یک محیط مشترک، ظرفیت را در واحدهای قابل تکرار افزایش می دهد.

3. اجزای اصلی معماری

3.1. Cell Router

Cell Router نقطه تصمیم گیری برای انتخاب مقصد درخواست است. این لایه باید ساده، سریع، قابل اتکا و تا حد ممکن بدون Business Logic باشد.

وظایف اصلی:

  1. استخراج Partition Key از درخواست یا هویت احراز شده.
  2. یافتن Cell مربوط به آن Partition Key.
  3. هدایت درخواست به Endpoint آن Cell.
  4. رعایت وضعیت سلامت و سیاست های Routing.
  5. مدیریت Cache اطلاعات Mapping.
  6. جلوگیری از هدایت درخواست های جدید به Cell ناسالم.

نمونه مفهومی:

Request:
  GET https://faridkarami.ir/api/profile

Authenticated User:
  user_id = 12045

Router:
  lookup(user_id) -> cell-2

Destination:
  https://cell-2.internal/api/profile

این نمونه صرفا یک الگوی مفهومی است؛ سایت عمومی لزوما نباید به این شکل مستقیما به Cellها Route شود.

نکته طراحی: Router نباید برای هر درخواست به یک سرویس مدیریتی کند وابسته باشد. اطلاعات Mapping می تواند در حافظه یا Cache محلی Router نگهداری شود و با مکانیزم مشخص به روز شود. Router نیز باید چند Replica مستقل داشته باشد تا خودش به Single Point of Failure تبدیل نشود.

3.2. Cells

هر Cell یک محیط عملیاتی مستقل است. بسته به نوع Workload ممکن است شامل موارد زیر باشد:

CELL 1
├── Ingress / Internal Load Balancer
├── Application API
├── Background Workers
├── Primary Database
├── Cache
├── Message Queue
├── Object Storage Namespace
├── Configuration
├── Secrets
└── Health Checks and Telemetry

همه Cellها لازم نیست دقیقا همین اجزا را داشته باشند. اصل مهم این است که هر Cell برای پردازش مسئولیت خود به منابع مشترک شکننده وابسته نباشد.

3.3. Control Plane

Control Plane مسئول عملیات مدیریتی است، نه پردازش عادی درخواست های کاربران.

وظایف متداول:

  • ثبت و Provision کردن Cell جدید
  • نگهداری Registry و وضعیت Cellها
  • مدیریت ظرفیت و محدودیت منابع
  • تخصیص Tenant یا Partition به Cell
  • انتقال کنترل شده کاربران میان Cellها
  • مدیریت نسخه و تنظیمات
  • آغاز Backup و بازیابی
  • مدیریت سیاست های Deployment
  • جمع آوری وضعیت عملیاتی و گزارش های سراسری

Control Plane باید از Data Plane جدا باشد. اگر Control Plane موقتا در دسترس نبود، Cellهای فعال بهتر است با آخرین اطلاعات معتبر Routing بتوانند فعالیت عادی خود را ادامه دهند.

3.4. Data Plane

Data Plane شامل Router و Cellهایی است که درخواست های واقعی کاربران را پردازش می کنند. باید تا حد ممکن از عملیات مدیریتی سنگین مستقل باشد.

3.5. Cell Registry

Registry اطلاعاتی مانند این موارد را نگهداری می کند:

cell_id
endpoint
region
status
capacity
software_version
created_at
last_health_check

و جدول تخصیص می تواند چنین ساختاری داشته باشد:

tenant_id       cell_id
-----------------------
tenant-1001     cell-1
tenant-1002     cell-2
tenant-1003     cell-1
tenant-1004     cell-3

Registry و Mapping دو مفهوم مرتبط اما متفاوت هستند: Registry درباره Cellها اطلاعات می دهد؛ Mapping مشخص می کند هر Partition به کدام Cell تعلق دارد.

4. طراحی یک Cell

4.1. اندازه Cell

Cellها نباید بدون محدودیت بزرگ شوند. اگر یک Cell بیش از حد بزرگ باشد، خرابی آن همچنان کاربران زیادی را تحت تاثیر قرار می دهد و مدیریت آن دشوار می شود.

در تعیین اندازه باید موارد زیر بررسی شوند:

  • تعداد کاربران فعال
  • نرخ درخواست در ثانیه (RPS)
  • حجم و نرخ رشد داده
  • CPU و RAM
  • ظرفیت Connectionهای Database
  • تعداد و زمان اجرای Jobها
  • ظرفیت Queue
  • هدف های Availability و Recovery
  • هزینه زیرساخت

اندازه مناسب برای همه سیستم ها یکسان نیست. بهتر است با Load Test، رفتار واقعی سیستم و هدف های Reliability تعیین شود.

4.2. مرز Cell

مرز Cell می تواند بر اساس یکی از این موارد تعریف شود:

  • Tenant یا مشتری
  • گروهی از کاربران
  • منطقه جغرافیایی
  • نوع Workload
  • محدوده داده یا Partition
  • ترکیبی از موارد بالا

برای SaaSهای چندمستاجری، Tenant یک Partition Key متداول است؛ اما اگر یک Tenant بسیار بزرگ باشد، ممکن است به Cell اختصاصی یا تقسیم داخلی بیشتری نیاز داشته باشد.

4.3. استقلال اجزا

در حالت ایده آل، Cellها نباید State عملیاتی مشترک داشته باشند. اشتراک زیرساخت هایی مانند Database، Queue یا Bucket می تواند مرز خرابی را تضعیف کند.

در عمل ممکن است اشتراک برخی سرویس ها به دلایل هزینه یا پیچیدگی اجتناب ناپذیر باشد. در این حالت باید اثر آن اشتراک، محدودیت منابع، سیاست های دسترسی و Failure Mode آن به صورت شفاف مستند شود.

5. انتخاب زبان برنامه نویسی

Cell-Based Architecture به زبان خاصی وابسته نیست. می توان همه اجزا را با یک زبان ساخت یا برای بخش های مختلف از زبان های متفاوت استفاده کرد.

زبان کاربرد مناسب ملاحظات

Node.js / TypeScript API، Router و سرویس های اکوسیستم مناسب و توسعه I/O محور سریع

Go Router، Control Plane و اجرای سبک و مناسب برای سرویس های زیرساختی سرویس های همزمان

Java / Kotlin Backendهای سازمانی و اکوسیستم بالغ و پردازش های پایدار ابزارهای گسترده

Python API، Data Processing و مناسب برای اکوسیستم AI داده و یادگیری ماشین

Rust اجزای حساس به کارایی و پیچیدگی توسعه و استخدام ایمنی حافظه بالاتر در برخی تیم ها

پیشنهاد عملی

اگر تیم با Node.js و NestJS تجربه دارد، می تواند Backend، Router و حتی Control Plane را با همین Stack پیاده کند. تغییر زبان به Go یا Rust صرفا به خاطر Cell-Based بودن ضروری نیست.

انتخاب زبان باید بر اساس مهارت تیم، نیاز Performance، اکوسیستم، هزینه نگهداری و پیچیدگی عملیاتی انجام شود.

6. انتخاب Database و استراتژی داده

6.1. PostgreSQL

PostgreSQL گزینه مناسبی برای داده های رابطه ای، تراکنش ها و بسیاری از Workloadهای SaaS است.

در یک طراحی Cell-Based می توان برای هر Cell یک Database مستقل داشت:

Cell 1 -> PostgreSQL Instance / Database 1
Cell 2 -> PostgreSQL Instance / Database 2
Cell 3 -> PostgreSQL Instance / Database 3

سطح جداسازی باید آگاهانه انتخاب شود:

  1. Schema جدا: جداسازی منطقی محدود؛ منابع Database مشترک هستند.
  2. Database جدا در یک Instance: جداسازی منطقی بیشتر، اما CPU، RAM و Failure Domain مشترک است.
  3. Instance جدا: استقلال عملیاتی بهتر، اما ممکن است ماشین یا Storage زیرین مشترک باشد.
  4. زیرساخت مستقل: جداسازی قوی تر، با هزینه و پیچیدگی بیشتر.

Databaseهای جدا روی یک سرور فیزیکی در برابر خرابی همان سرور مستقل نیستند.

6.2. MongoDB

MongoDB برای مدل های Document-oriented مناسب است. استفاده از آن باید بر اساس نیاز مدل داده و Queryها باشد، نه صرفا به دلیل استفاده از معماری Cell-Based.

6.3. Redis

کاربردهای متداول:

  • Cache
  • Rate Limiting
  • Sessionهای موقت
  • داده های موقت و کوتاه عمر
  • برخی الگوهای هماهنگی، با رعایت محدودیت های آن

برای Isolation بهتر، Redis هر Cell می تواند مستقل یا دست کم با مرزبندی و محدودیت منابع دقیق باشد.

6.4. Search و Analytics

ابزارهای مکمل:

فناوری کاربرد

OpenSearch / Elasticsearch جستجو و Indexهای خواندنی ClickHouse تحلیل داده و Queryهای تحلیلی Data Lake نگهداری داده های تحلیلی و تاریخی Object Storage فایل ها، رسانه ها و خروجی های Backup

Search Index مرکزی می تواند داده های منتخب چند Cell را برای جستجوی سراسری تجمیع کند. در این مدل، Index معمولا Read Model است و منبع اصلی داده در Cell مالک باقی می ماند.

6.5. الگوی مالکیت داده

برای هر موجودیت باید مشخص باشد کدام Cell مالک داده است.

اصول مهم:

  • یک منبع معتبر برای نوشتن هر داده تعیین شود.
  • از نوشتن همزمان و بدون هماهنگی در چند Cell اجتناب شود.
  • داده های تجمیعی با Event یا CDC ساخته شوند.
  • داده های Read Model قابلیت بازسازی داشته باشند.
  • سازگاری نهایی (Eventual Consistency) در بخش هایی که لازم است پذیرفته و مستند شود.

7. ابزارها و فناوری های پیشنهادی

هیچ ابزار اجباری یا محصول واحدی برای پیاده سازی Cell-Based Architecture وجود ندارد. انتخاب ها به اندازه سیستم، Cloud Provider، مهارت تیم و نیازهای Availability بستگی دارند.

7.1. Containerization

Docker

برای بسته بندی برنامه، Worker و وابستگی های اجرایی در Container استفاده می شود.

مزایا: - محیط اجرای قابل تکرار - جداسازی فرآیندها - ساده تر شدن Deployment - سازگاری بهتر محیط توسعه و Production

7.2. Orchestration

ابزار کاربرد

Kubernetes Orchestration در مقیاس بزرگ K3s توزیع سبک Kubernetes Amazon ECS اجرای Container در AWS Docker Compose توسعه محلی و محیط های ساده Nomad زمان بندی و اجرای Workload

Kubernetes به تنهایی معماری Cell-Based ایجاد نمی کند. باید مرز Cellها، Namespaceها، Clusterها، Databaseها، Routing و سیاست های جداسازی نیز طراحی شوند.

می توان چند Cell را در یک Kubernetes Cluster اجرا کرد، اما در این حالت خرابی خود Cluster همچنان ممکن است چند Cell را همزمان تحت تاثیر قرار دهد. برای Isolation قوی تر می توان از Clusterها یا Failure Domainهای مستقل استفاده کرد.

7.3. Reverse Proxy و Routing

ابزار کاربرد

NGINX Reverse Proxy و Load Balancing Envoy Proxy و Traffic Management HAProxy Load Balancing Traefik Routing و Discovery در محیط های Container

این ابزارها می توانند بخشی از Routing را انجام دهند، اما منطق تخصیص Partition به Cell معمولا به Registry یا Cell Router نیاز دارد.

7.4. Message Broker

ابزار کاربرد و ملاحظات

RabbitMQ صف پیام و Work Queue Apache Kafka Event Streaming با حجم بالا و نگهداری جریان رویداد NATS Messaging سبک و ارتباطات سریع Redis Streams سناریوهای ساده تر مبتنی بر Redis

انتخاب Broker باید با الگوی مصرف پیام، نیاز به Replay، ترتیب پیام، دوام داده و مدل عملیاتی هماهنگ باشد.

برای حفظ Isolation، Queueهای Cellها را جدا یا با Quota و سیاست های سخت گیرانه محدود کنید. یک Broker مشترک بدون محدودیت می تواند تبدیل به نقطه فشار مشترک شود.

7.5. Observability

ابزار مسئولیت

Prometheus جمع آوری Metrics Grafana داشبورد و Visualization Loki تجمیع Log OpenTelemetry استاندارد Instrumentation و Telemetry Jaeger / Tempo Distributed Tracing Alertmanager مدیریت Alertها

شاخص های مهم برای هر Cell:

  • Request Rate
  • Error Rate
  • Latency در صدک های مختلف
  • CPU و RAM
  • Database Connections
  • Database Replication Lag
  • Queue Depth
  • Worker Lag
  • Disk Usage
  • وضعیت Health Check
  • تعداد کاربران و Tenantهای تخصیص یافته

7.6. Infrastructure as Code و Deployment

ابزار کاربرد

Terraform ساخت و مدیریت زیرساخت OpenTofu ابزار متن باز Infrastructure as Code Helm بسته بندی و نصب برنامه در Kubernetes Argo CD GitOps و همگام سازی وضعیت Cluster با Git Ansible پیکربندی و Automation سرورها GitHub Actions CI/CD و اجرای Pipeline AWS CloudFormation تعریف زیرساخت در AWS AWS Step Functions Orchestration فرایندهای مدیریتی در AWS

یک هدف مهم این است که ساخت Cell جدید به فرایندی خودکار، تکرارپذیر و قابل ممیزی تبدیل شود.

8. Routing و تخصیص کاربران به Cellها

یکی از تصمیمات اصلی، انتخاب Partition Key و الگوریتم تخصیص است.

8.1. Hash-Based Routing

در ساده ترین روش:

const cellIndex = hash(partitionKey) % totalCells;

مزیت: - ساده و سریع - بدون نیاز به Mapping برای هر کاربر

عیب: - با تغییر تعداد Cellها، تعداد زیادی از تخصیص ها ممکن است تغییر کند. - انتقال کنترل شده و انتخاب دستی Cell دشوارتر است.

8.2. Consistent Hashing

در Consistent Hashing، اضافه یا حذف Node معمولا باعث جابه جایی محدودتری نسبت به Hash ساده می شود.

این روش برای برخی سیستم های توزیع شده مفید است، اما به تنهایی جایگزین Registry، مدیریت ظرفیت و فرایند Migration نیست.

8.3. Mapping Table

در این روش تخصیص به صورت صریح نگهداری می شود:

partition_key     cell_id
-------------------------
tenant-1001       cell-1
tenant-1002       cell-2
tenant-1003       cell-1
tenant-1004       cell-3

مزایا: - کنترل دقیق روی تخصیص - امکان انتقال Tenant - پشتیبانی از Cell اختصاصی برای مشتری بزرگ - تغییر تعداد Cellها بدون تغییر الگوریتم Hash - امکان مدیریت ظرفیت و سیاست های تخصیص

معایب: - نیاز به Registry قابل اتکا - Cache و Invalidation اطلاعات Mapping - نیاز به فرایند امن برای انتقال Partition

برای بسیاری از SaaSهای چندمستاجری، Mapping Table گزینه عملی و قابل کنترل تری است.

8.4. نکات امنیتی Routing

Router نباید صرفا به tenant_id ارسالی از Client اعتماد کند. ابتدا باید هویت کاربر و مجوز دسترسی احراز شود و سپس Partition Key معتبر از Context مورد اعتماد استخراج شود.

همچنین: - مقصد داخلی Cell نباید از ورودی دلخواه Client پذیرفته شود. - ارتباط Router تا Cell باید احراز هویت و رمزنگاری شود. - تغییر Mapping باید Audit Log داشته باشد. - Cache قدیمی نباید موجب ارسال درخواست به Cell اشتباه شود. - در انتقال Cell باید رفتار درخواست های در حال اجرا مشخص باشد.

9. ارتباط بین Cellها و داده های سراسری

فرض کنیم کاربر A در Cell 1 و کاربر B در Cell 2 قرار دارد. کاربر A محتوایی منتشر می کند و کاربر B باید بتواند آن را در جستجو یا Feed مشاهده کند.

چند الگوی رایج وجود دارد:

9.1. Event Replication

Cell مالک پس از ثبت تغییر، Event منتشر می کند:

Cell 1
  |
  | ContentPublished
  v
Event Broker
  |
  +----> Search Indexer
  |
  +----> Feed Read Model
  |
  +----> Analytics Pipeline

این روش برای ساخت Read Modelهای تجمیعی مفید است.

9.2. API Communication

یک Cell در صورت نیاز می تواند از API کنترل شده Cell دیگر استفاده کند. این ارتباط باید محدود، احراز هویت شده، دارای Timeout و سیاست Retry باشد.

ارتباط همزمان و زنجیره ای بین Cellها را به حداقل برسانید؛ چون دسترس پذیری چند Cell را به هم وابسته می کند.

9.3. Central Read Model

برای جستجو، Feed عمومی، گزارش گیری و Discovery می توان یک Read Model مرکزی ساخت.

ویژگی های مهم: - فقط داده های مورد نیاز در آن کپی شود. - منبع اصلی داده در Cell مالک باقی بماند. - Read Model قابل بازسازی باشد. - تاخیر همگام سازی اندازه گیری شود. - اطلاعات حساس بدون نیاز وارد لایه مرکزی نشود.

9.4. Transactional Outbox

برای جلوگیری از حالتی که Database تغییر کند اما Event منتشر نشود، می توان از الگوی Transactional Outbox استفاده کرد.

در یک تراکنش Database: 1. داده اصلی ثبت می شود. 2. رکورد Event در جدول Outbox ذخیره می شود. 3. یک Worker رکورد Outbox را منتشر می کند. 4. Event پس از تایید انتشار علامت گذاری می شود.

مصرف کننده ها نیز باید Idempotent باشند؛ یعنی دریافت دوباره یک Event باعث اجرای تکراری و مخرب عملیات نشود.

10. مدیریت خرابی و بازیابی

فرض کنیم Cell 2 دچار مشکل شده است.

Cell 1: HEALTHY
Cell 2: FAILED
Cell 3: HEALTHY

فرایند پیشنهادی:

  1. Monitoring خرابی یا افزایش غیرعادی Error Rate را تشخیص می دهد.
  2. Cell 2 از دریافت ترافیک جدید خارج می شود.
  3. درخواست های در حال اجرا طبق سیاست Timeout و Drain مدیریت می شوند.
  4. سایر Cellها بدون وابستگی به Cell 2 به کار ادامه می دهند.
  5. تیم یا Automation علت خرابی را بررسی می کند.
  6. Cell از طریق Restart، Restore یا Reprovision بازیابی می شود.
  7. پس از Health Check و Readiness، ترافیک به آن باز می گردد.

نکته مهم درباره انتقال کاربران

خارج کردن یک Cell از Routing به معنی انتقال خودکار داده های آن نیست. برای انتقال کاربران باید: - منبع داده مشخص باشد. - Backup و Replication معتبر وجود داشته باشد. - Writeها در زمان انتقال کنترل شوند. - وضعیت درخواست های در حال اجرا تعیین شود. - Mapping تنها در زمان مناسب تغییر کند. - امکان Rollback وجود داشته باشد.

اهداف بازیابی

برای هر Cell باید دو هدف تعریف شود:

  • RTO: حداکثر زمان قابل قبول برای بازیابی سرویس.
  • RPO: حداکثر میزان قابل قبول از دست رفتن داده بر حسب زمان.

این اهداف روی Backup، Replication، معماری Database و هزینه زیرساخت اثر مستقیم دارند.

خرابی های مشترک

حتی با Cellهای مستقل، موارد زیر می توانند چند Cell را همزمان تحت تاثیر قرار دهند:

  • خرابی Region یا شبکه مشترک
  • Router مرکزی معیوب
  • DNS یا Identity Provider مشترک
  • Secret یا Configuration اشتباه و سراسری
  • Deployment همزمان و معیوب
  • Database یا Broker مشترک
  • محدودیت منابع در Host یا Cluster مشترک

بنابراین Cell-Based Architecture باید همراه با طراحی Failure Domain، Redundancy و کنترل وابستگی های مشترک باشد.

11. Deployment و مدیریت چرخه عمر Cellها

11.1. Cell Template

برای تمام Cellها یک Template استاندارد تعریف کنید. این Template شامل موارد زیر است:

  • نسخه Application
  • تنظیمات Runtime
  • منابع CPU و RAM
  • Database و Migration
  • Cache و Queue
  • Network Policy
  • Secrets
  • Monitoring
  • Health Check
  • Backup Policy

11.2. Canary Deployment

نسخه جدید ابتدا روی یک Cell آزمایشی یا گروه کوچکی از Cellها منتشر می شود. سپس Metrics و Errorها بررسی می شوند. اگر نتیجه مطلوب بود، انتشار مرحله ای ادامه پیدا می کند.

Build
  |
  v
Deploy to Canary Cell
  |
  v
Health + Metrics Check
  |
  +---- Failure ----> Rollback / Stop
  |
  v
Deploy to Small Cell Group
  |
  v
Observe
  |
  v
Progressive Rollout

از انتشار همزمان نسخه جدید به تمام Cellها اجتناب کنید؛ این کار یکی از مزیت های اصلی معماری را از بین می برد.

11.3. Cell Provisioning

فرایند ایجاد Cell جدید می تواند چنین باشد:

  1. Control Plane درخواست ایجاد Cell را دریافت می کند.
  2. ظرفیت و محدودیت ها بررسی می شوند.
  3. زیرساخت از روی Template ساخته می شود.
  4. Database و Schema آماده می شوند.
  5. سرویس ها Deploy می شوند.
  6. Health Check اجرا می شود.
  7. Cell در Registry ثبت می شود.
  8. پس از تایید، Partitionهای جدید به آن تخصیص می یابند.

11.4. Cell Rebalancing

وقتی یک Cell به آستانه ظرفیت نزدیک می شود، می توان بخشی از Partitionها را به Cell دیگر منتقل کرد.

این فرایند باید با کنترل Writeها، انتقال داده، اعتبارسنجی، تغییر Mapping و امکان Rollback انجام شود. تغییر ساده یک سطر Mapping بدون انتقال یا همگام سازی داده کافی نیست.

12. امنیت و جداسازی

Cell-Based بودن به تنهایی امنیت Tenantها را تضمین نمی کند. کنترل های امنیتی باید در تمام لایه ها اعمال شوند.

چک لیست مهم:

  • احراز هویت و Authorization در API
  • استخراج Tenant از هویت معتبر، نه ورودی قابل جعل
  • Network Segmentation بین Cellها
  • Secret مستقل یا Scope شده برای هر Cell
  • رمزنگاری ارتباطات داخلی
  • رمزنگاری داده در حالت ذخیره
  • Least Privilege برای Database و سرویس ها
  • Audit Log برای عملیات مدیریتی
  • Rate Limit و Quota به تفکیک Tenant و Cell
  • Backup رمزنگاری شده
  • مدیریت امن کلیدها و Rotation
  • جلوگیری از دسترسی مستقیم Client به سرویس های داخلی

برای محیط های حساس، جداسازی می تواند تا سطح Account، Subscription، Project یا Cluster مستقل گسترش پیدا کند.

13. مزایا، معایب و Anti-Patternها

مزایا

  • محدود شدن محدوده اثر خرابی
  • کاهش اثر Deployment معیوب
  • مقیاس پذیری افقی با افزودن Cell
  • امکان تخصیص منابع متناسب با هر گروه
  • جداسازی عملیاتی Tenantها
  • امکان Cell اختصاصی برای مشتریان بزرگ
  • بازیابی و مانیتورینگ مستقل
  • کنترل بهتر روی ظرفیت و هزینه در مقیاس بالا

معایب

  • پیچیدگی بیشتر در طراحی و عملیات
  • افزایش هزینه Database و زیرساخت
  • دشواری Migration و انتقال داده
  • پیچیدگی گزارش گیری سراسری
  • نیاز به Control Plane و Registry
  • نیاز به Observability دقیق
  • پیچیدگی مدیریت نسخه و Configuration
  • دشواری سازگاری داده میان Cellها

Anti-Patternهای رایج

  1. Cellهای بدون محدودیت اندازه: Cell بزرگ، Blast Radius بزرگی دارد.
  2. Shared Database بدون کنترل: خرابی Database مشترک می تواند تمام Cellها را مختل کند.
  3. Shared Queue بدون Quota: یک Cell پرمصرف می تواند منابع همه را اشغال کند.
  4. Router پیچیده: Business Logic در Router آن را به نقطه شکست حساس تبدیل می کند.
  5. Cross-Cell Calls زیاد: وابستگی همزمان، Isolation را تضعیف می کند.
  6. Deployment همزمان: انتشار معیوب می تواند تمام Cellها را درگیر کند.
  7. نبود Rebalancing Plan: اضافه کردن Cell بدون راه انتقال داده و Partition کافی نیست.
  8. نادیده گرفتن Failure Domain: چند Cell روی یک Host یا Cluster ممکن است با یک خرابی از دست بروند.
  9. اعتماد به Hash ساده برای همه شرایط: تغییر تعداد Cellها می تواند تخصیص ها را جابه جا کند.
  10. فرض استقلال کامل بدون آزمون: باید با Failure Injection و تست عملی اثبات شود.

14. مقایسه با معماری های دیگر

Cell-Based در برابر Microservices

موضوع Microservices Cell-Based

محور تقسیم قابلیت و مسئولیت نرم گروه درخواست ها، افزاری کاربران یا داده ها

هدف اصلی استقلال توسعه و استقرار محدود کردن Blast Radius سرویس ها

واحد اصلی Service Cell

Database معمولا مالکیت داده در داده های عملیاتی مستقل سطح سرویس در سطح Cell

ارتباطات API و Messaging میان ارتباط میان Cellها باید سرویس ها حداقلی باشد

ترکیب پذیری می تواند داخل هر Cell می تواند شامل چند استفاده شود Microservice باشد

Cell-Based جایگزین Microservices نیست. یک Cell می تواند از چند Microservice تشکیل شده باشد.

Cell-Based در برابر Modular Monolith

Modular Monolith روی مرزبندی ماژول های داخل یک برنامه و یک Deployment تمرکز دارد. Cell-Based روی تکرار واحدهای عملیاتی مستقل و تقسیم Workload تمرکز می کند.

برای بسیاری از محصولات، Modular Monolith نقطه شروع ساده تر و کم هزینه تری است.

Cell-Based در برابر Sharding

Sharding داده یا بار را بین چند Partition تقسیم می کند. Cell-Based معمولا یک سطح بالاتر است: علاوه بر داده، اجزای اجرای برنامه و منابع لازم برای پردازش Workload را نیز در واحدهای مستقل قرار می دهد.

Sharding می تواند یکی از تکنیک های داخلی Cell-Based Architecture باشد.

Cell-Based در برابر Multi-Region

Multi-Region درباره توزیع سیستم در چند منطقه جغرافیایی است. Cell-Based درباره ساخت مرزهای مستقل Workload است. می توان چند Cell در یک Region یا Cellهایی در چند Region داشت.

15. نمونه طراحی برای یک وب سایت

این بخش یک مثال آموزشی برای یک وب سایت فرضی با دامنه faridkarami.ir است. هدف، نشان دادن الگوی طراحی است و به معنی ادعای وجود چنین زیرساختی برای این دامنه نیست.

فرض کنیم وب سایت در آینده شامل حساب کاربران، محتوای منتشرشده، جستجو، اعلان ها و پردازش رسانه باشد.

15.1. تقسیم مسئولیت

  • کاربران و داده های حساب می توانند بر اساس User ID یا Account ID تقسیم شوند.
  • محتوای متعلق به یک حساب می تواند در Cell مالک همان حساب ذخیره شود.
  • جستجوی عمومی می تواند از Search Index تجمیع شده استفاده کند.
  • پردازش تصویر و ویدئو می تواند از Workerهای مستقل و Queueهای کنترل شده استفاده کند.
  • Analytics می تواند از Eventهای Cellها تغذیه شود.

15.3. جریان یک درخواست

فرض کنیم کاربری وارد faridkarami.ir می شود و درخواست مشاهده پروفایل را ارسال می کند.

  1. درخواست از Edge و Gateway عبور می کند.
  2. هویت کاربر اعتبارسنجی می شود.
  3. Router کلید Partition معتبر را استخراج می کند.
  4. Mapping مشخص می کند کاربر در Cell 2 قرار دارد.
  5. درخواست به API همان Cell هدایت می شود.
  6. API داده را از Database و Cache همان Cell می خواند.
  7. پاسخ به Client برمی گردد.

15.4. جستجوی سراسری

برای جستجوی محتوا در تمام Cellها، درخواست ها نباید لزوما به تک تک Cellها ارسال شوند. بهتر است Eventهای تغییر محتوا به یک Search Index مرکزی منتقل شوند.

در این مدل: - Database هر Cell منبع اصلی داده است. - Search Index نسخه قابل جستجوی داده هاست. - Indexer با Eventها به روز می شود. - در صورت نیاز Index از داده های اصلی بازسازی می شود.

15.5. نکته درباره فایل ها و رسانه ها

Object Storage می تواند Shared باشد، اما Shared بودن آن باید با طراحی مناسب Bucket، Prefix، IAM، Quota، Availability و Failure Domain همراه باشد. اگر Object Storage مشترک از دسترس خارج شود، چند Cell ممکن است تحت تاثیر قرار گیرند.

در صورت نیاز به Isolation قوی تر، می توان Storage Namespace یا حتی زیرساخت ذخیره سازی مستقل برای هر Cell در نظر گرفت.

16. مسیر مهاجرت مرحله ای

مهاجرت مستقیم از یک معماری ساده به Cell-Based کامل معمولا پرهزینه و پرریسک است. مسیر تدریجی پیشنهاد می شود.

مرحله 1: آماده سازی Domainها

  • مرز ماژول ها را مشخص کنید.
  • مالکیت هر جدول و موجودیت را تعیین کنید.
  • وابستگی های مستقیم میان ماژول ها را کاهش دهید.
  • APIهای داخلی مشخص تعریف کنید.

مرحله 2: آماده سازی Multi-Tenancy

  • Tenant ID یا Partition Key را در مدل داده ها تعریف کنید.
  • دسترسی به داده ها را در سطح Tenant کنترل کنید.
  • Queryها و Indexها را برای Partition Key بررسی کنید.
  • تست های جلوگیری از نشت داده میان Tenantها بسازید.

مرحله 3: جداسازی پردازش های پس زمینه

  • Workerها را از API جدا کنید.
  • Jobها را Idempotent طراحی کنید.
  • Retry و Dead Letter Queue تعریف کنید.
  • برای Tenantهای پرمصرف Quota در نظر بگیرید.

مرحله 4: Event-Driven کردن بخش های مناسب

  • Eventهای دامنه ای مشخص تعریف کنید.
  • از Transactional Outbox در موارد لازم استفاده کنید.
  • مصرف کننده های Idempotent بسازید.
  • Read Modelهای تجمیعی را جدا کنید.

مرحله 5: ساخت Control Plane و Registry

  • مدل Cell و وضعیت آن را تعریف کنید.
  • Mapping میان Partition و Cell بسازید.
  • ظرفیت و Health هر Cell را ثبت کنید.
  • عملیات Provisioning و Deprovisioning را خودکار کنید.

مرحله 6: ساخت Cell دوم

ابتدا یک گروه محدود و قابل کنترل از کاربران یا Tenantها را به Cell دوم منتقل کنید. مسیر انتقال، Backup، Restore، Routing و Rollback را در محیط آزمایشی تمرین کنید.

مرحله 7: Canary و Rebalancing

  • Deployment مرحله ای بسازید.
  • انتقال Partition را خودکار و قابل ممیزی کنید.
  • سناریوهای خرابی را آزمایش کنید.
  • ظرفیت و اندازه Cellها را با داده واقعی تنظیم کنید.

چه زمانی مهاجرت توجیه دارد؟

وقتی یکی یا چند مورد زیر به شکل واقعی مشاهده شود: - یک گروه از کاربران منابع سایر کاربران را مصرف می کند. - نیاز به محدود کردن اثر خرابی یا Deployment وجود دارد. - Database یا Workload مشترک به گلوگاه تبدیل شده است. - مشتریان بزرگ نیاز به Isolation اختصاصی دارند. - تیم توان عملیاتی مدیریت چند محیط مستقل را دارد.

صرف پیش بینی رشد آینده، به تنهایی دلیل کافی برای ساخت تعداد زیادی Cell نیست.

17. چک لیست طراحی و اجرا

طراحی معماری

  • Partition Key مشخص است.
  • مرز و مسئولیت هر Cell مشخص است.
  • اندازه و سقف منابع Cell تعریف شده است.
  • Control Plane از Data Plane جدا شده است.
  • Router ساده و قابل توسعه است.
  • وابستگی های مشترک مستند شده اند.

داده و سازگاری

  • مالکیت داده هر موجودیت مشخص است.
  • استراتژی Database Isolation تعریف شده است.
  • Backup و Restore هر Cell آزمایش شده است.
  • Eventها دارای نسخه و قرارداد مشخص هستند.
  • Outbox و Idempotency در موارد لازم پیاده شده اند.
  • Read Modelهای مرکزی قابل بازسازی هستند.

عملیات و Reliability

  • Health Check و Readiness تعریف شده اند.
  • Metrics در سطح Cell جمع آوری می شوند.
  • Log و Trace دارای Cell ID هستند.
  • Canary Deployment وجود دارد.
  • Rollback آزمایش شده است.
  • RTO و RPO تعیین شده اند.
  • خرابی یک Cell در محیط آزمایشی شبیه سازی شده است.
  • خرابی Router و سرویس های مشترک نیز بررسی شده است.

امنیت

  • Tenant از هویت معتبر استخراج می شود.
  • دسترسی بین Cellها محدود است.
  • Secretها مدیریت و Rotation می شوند.
  • ارتباطات داخلی رمزنگاری شده اند.
  • Audit Log برای عملیات مدیریتی وجود دارد.
  • Quota و Rate Limit تعریف شده اند.

مقیاس پذیری

  • ظرفیت هر Cell قابل اندازه گیری است.
  • Provisioning خودکار وجود دارد.
  • Rebalancing Plan وجود دارد.
  • انتقال Partition قابل Rollback است.
  • هزینه عملیاتی هر Cell قابل مشاهده است.

جمع بندی نهایی

Cell-Based Architecture روشی برای تقسیم یک Workload بزرگ به واحدهای مستقل و قابل تکرار است. ارزش اصلی آن فقط افزایش تعداد سرورها یا تقسیم Database نیست؛ بلکه ساخت مرزهای خرابی مشخص، محدود کردن اثر تغییرات و فراهم کردن امکان توسعه تدریجی ظرفیت است.

چند اصل را باید همیشه به خاطر داشت:

  1. هر Cell باید تا حد ممکن برای پردازش Workload خودش مستقل باشد.
  2. Router باید ساده، سریع و Highly Available باشد.
  3. Control Plane باید از پردازش عادی کاربران جدا بماند.
  4. وابستگی های مشترک می توانند مزیت Isolation را از بین ببرند.
  5. انتقال کاربران و داده ها نیازمند فرایند دقیق و قابل Rollback است.
  6. Deployment باید مرحله ای باشد، نه همزمان برای همه Cellها.
  7. Cell-Based Architecture جایگزین Microservices نیست و می تواند درون هر Cell از Microservices استفاده کند.
  8. این معماری برای همه پروژه ها لازم نیست؛ پیچیدگی آن باید با نیاز واقعی سیستم توجیه شود.
