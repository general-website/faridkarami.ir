راهنمای کامل TWA

ساخت اپلیکیشن اندروید برای وب سایت با TWA و Bubblewrap

مقدمه

اگر یک وب اپلیکیشن واکنش گرا دارید، برای ارائه نسخه اندروید آن لزوما مجبور نیستید رابط کاربری را با Kotlin یا Java از ابتدا بازنویسی کنید. یکی از راه های ارائه نسخه اندروید، استفاده از Trusted Web Activity (TWA) است.

TWA به اپلیکیشن اندروید اجازه می دهد محتوای یک وب اپلیکیشن را با استفاده از مرورگر مورد اعتماد، معمولا Chrome، در یک پنجره تمام صفحه اجرا کند. در صورت تنظیم صحیح، تجربه کاربر شبیه یک اپلیکیشن اندرویدی است و نوار آدرس معمول مرورگر نمایش داده نمی شود.

در این مقاله، مسیر ساخت نسخه اندروید پروژه FaridKarami برای آدرس https://app.faridkarami.ir را با ابزار Bubblewrap مرور می کنیم؛ از آماده سازی محیط توسعه و ساخت پروژه تا رفع خطاهای Build، امضای APK، تنظیم assetlinks.json و انتشار فایل برای دانلود مستقیم.

این راهنما بر اساس تجربه عملی ساخت پروژه نوشته شده است. مسیرها، نسخه ابزارها و شناسه بسته ممکن است در پروژه های دیگر متفاوت باشند.

۱. TWA چیست و چه زمانی انتخاب مناسبی است؟

Trusted Web Activity قابلیتی در اکوسیستم اندروید است که محتوای وب را از طریق مرورگر مورد اعتماد اجرا می کند.

در این معماری:

  • رابط کاربری و بخش عمده منطق برنامه در وب اپلیکیشن باقی می ماند.
  • اپلیکیشن اندروید نقش میزبان اجرای وب اپلیکیشن را دارد.
  • بسیاری از تغییرات وب با انتشار نسخه جدید سایت اعمال می شوند و لزوما به انتشار APK جدید نیاز ندارند.
  • برای تایید رابطه اعتماد بین اپ اندروید و دامنه وب از Digital Asset Links استفاده می شود.

تفاوت TWA و WebView

در روش WebView، توسعه دهنده یک WebView داخل اپ اندروید قرار می دهد و باید جزئیات بیشتری مانند رفتار مرورگر، فایل ها، لینک های خارجی و چرخه عمر WebView را مدیریت کند.

در TWA، محتوا با موتور مرورگر مورد اعتماد اجرا می شود. این روش برای وب اپلیکیشن هایی مناسب است که از قبل تجربه کاربری مناسبی روی موبایل دارند و می خواهند با حداقل کدنویسی Native نسخه اندروید ارائه کنند.

TWA جایگزین کامل توسعه Native نیست. اگر برنامه به قابلیت های عمیق سیستم عامل، پردازش های پس زمینه پیچیده یا کنترل گسترده Native نیاز داشته باشد، توسعه Native یا معماری ترکیبی ممکن است مناسب تر باشد.

وابستگی به Chrome

TWA به یک مرورگر سازگار با Trusted Web Activity نیاز دارد. در بسیاری از دستگاه ها این مرورگر Chrome است؛ بنابراین TWA را نباید یک WebView مستقل و کاملا جدا از مرورگر در نظر گرفت.

۲. معماری پروژه FaridKarami

در پروژه مورد بررسی دو بخش وب وجود داشت:

  • وب سایت اصلی FaridKarami روی https://faridkarami.ir که با آن کاری نداریم.
  • وب اپلیکیشن روی https://app.faridkarami.ir که قرار بود در قالب اپ اندرویدی اجرا شود.

هدف، ساخت اپلیکیشن اندروید برای وب اپلیکیشن بود، نه تبدیل وب سایت محتوایی اصلی به اپ.

بنابراین آدرس شروع TWA باید این باشد:

https://app.faridkarami.ir

پیش از شروع مطمئن شوید وب اپلیکیشن روی موبایل به درستی کار می کند، HTTPS فعال است و مسیرهای اصلی آن بدون خطا باز می شوند.

۳. آماده سازی ابزارهای مورد نیاز

برای ساخت پروژه از Bubblewrap استفاده می کنیم. این ابزار خط فرمان، پروژه اندرویدی مبتنی بر TWA را تولید می کند.

ابتدا Node.js و npm را آماده کنید و سپس Bubblewrap را به صورت سراسری نصب کنید:

npm install -g @bubblewrap/cli

نسخه نصب شده را بررسی کنید:

bubblewrap --version

Bubblewrap ممکن است برای آماده سازی محیط توسعه، نصب JDK و Android SDK را پیشنهاد دهد.

نصب JDK

در این پروژه، نصب JDK 17 از طریق خود Bubblewrap انجام شد. مسیر نصب در محیط مورد استفاده چنین بود:

C:\Users\Computer\.bubblewrap\jdk\jdk-17.0.11+9

مسیر سیستم شما ممکن است متفاوت باشد.

در یکی از مراحل، دریافت فایل فشرده JDK Sources با خطای زیر مواجه شد:

cli ERROR end of central directory record signature not found

این خطا معمولا به فایل ZIP ناقص یا خراب اشاره دارد. خطای دریافت Sources لزوما به معنی نصب نشدن خود JDK نیست. ابتدا وجود JDK و ابزارهای آن را بررسی کنید.

پیدا کردن keytool در Windows

برای کار با Keystore به ابزار keytool نیاز داریم. اگر اجرای دستور زیر با پیام شناخته نشدن دستور مواجه شد:

keytool

ممکن است مسیر پوشه bin مربوط به JDK در PATH نباشد.

برای پیدا کردن فایل اجرایی:

Get-ChildItem "$env:USERPROFILE\.bubblewrap\jdk" -Recurse -Filter keytool.exe

سپس می توانید آن را با مسیر کامل اجرا کنید:

& "$env:USERPROFILE\.bubblewrap\jdk\jdk-17.0.11+9\bin\keytool.exe" -help

۴. ساخت پروژه TWA با Bubblewrap

در پوشه ای که می خواهید پروژه اندروید در آن ساخته شود، دستور زیر را اجرا کنید:

bubblewrap init --manifest https://app.faridkarami.ir/manifest.webmanifest

آدرس Manifest باید با آدرس واقعی فایل Web App Manifest پروژه جایگزین شود. اگر فایل در مسیر دیگری قرار دارد، همان مسیر را وارد کنید.

Bubblewrap اطلاعات مورد نیاز را از Manifest می خواند و برای تکمیل تنظیمات پروژه چند سوال می پرسد.

آدرس شروع برنامه

آدرس شروع باید وب اپلیکیشن مورد نظر باشد:

https://app.faridkarami.ir

آیکون اصلی برنامه

برای آیکون اصلی از تصویر با کیفیت و ابعاد مناسب استفاده کنید. تصویر PNG با ابعاد 512 در 512 پیکسل انتخاب مناسبی برای آیکون اصلی است.

Monochrome Icon

Bubblewrap ممکن است آدرس Monochrome Icon را نیز درخواست کند. این آیکون با آیکون اصلی تفاوت دارد و برای موقعیت هایی مانند نمایش آیکون تک رنگ در اندروید استفاده می شود.

در این پروژه ابتدا آدرس favicon.ico وارد شد و خطای زیر رخ داد:

cli ERROR Unsupported MIME type: image/x-icon

علت این بود که ورودی با MIME type برابر image/x-icon تشخیص داده شد و برای این مورد مناسب نبود.

راه حل، ارائه یک فایل PNG معتبر است. بهتر است تصویر Monochrome ساده، تک رنگ و با پس زمینه شفاف باشد. صرفا خاکستری کردن لوگوی رنگی لزوما یک آیکون Monochrome مناسب تولید نمی کند.

دسترسی های برنامه

Bubblewrap درباره قابلیت ها و دسترسی های مورد نیاز سوال می کند. انتخاب هر مورد باید بر اساس نیاز واقعی وب اپلیکیشن باشد. اگر برنامه از موقعیت مکانی استفاده می کند، دسترسی Geolocation می تواند لازم باشد.

در پروژه FaridKarami دسترسی Geolocation فعال شد.

Google Play Billing

اگر برنامه از پرداخت درون برنامه ای Google Play استفاده نمی کند، فعال کردن Play Billing ضرورتی ندارد. در این پروژه این گزینه فعال نشد.

۵. شناسه بسته، applicationId و namespace

یکی از تنظیمات مهم پروژه، شناسه یکتای اپلیکیشن اندروید است.

در پروژه FaridKarami، مقادیر فایل app/build.gradle به این شکل بودند:

applicationId "ir.faridkarami.app.twa"
namespace "ir.faridkarami.app.twa"

این دو مقدار در Gradle کاربردهای مرتبط اما متمایزی دارند. برای تنظیم Digital Asset Links، مقدار مهم applicationId است.

نکته مهم: مقدار namespace در فایل assetlinks.json با namespace در Gradle یکی نیست. در Digital Asset Links مقدار زیر باید دقیقا android_app باشد:

"namespace": "android_app"

در مقابل، مقدار package_name باید با applicationId اپلیکیشن اندروید مطابقت داشته باشد:

"package_name": "ir.faridkarami.app.twa"

برای بررسی مقادیر پروژه در PowerShell:

Select-String -Path .\app\build.gradle -Pattern 'applicationId|namespace'

شناسه بسته را پس از انتشار عمومی بدون برنامه ریزی تغییر ندهید؛ Android از آن برای تشخیص هویت اپلیکیشن و به روزرسانی های بعدی استفاده می کند.

۶. ساخت Keystore و امضای اپلیکیشن

فایل APK برای انتشار باید امضا شود. امضای اپلیکیشن اندروید با کلید خصوصی موجود در Keystore انجام می شود.

در این پروژه مسیر Keystore چنین انتخاب شد:

E:\projects\faridkarami\projects\app-faridkarami-android\android.keystore

نام Alias نیز این بود:

android

در زمان ساخت Keystore، اطلاعات گواهی مانند نام، واحد سازمانی، سازمان و کشور درخواست می شود.

Keystore را جدی بگیرید

فایل Keystore و رمزهای آن را با دقت نگهداری کنید:

  • از فایل Keystore نسخه پشتیبان امن تهیه کنید.
  • رمز Keystore و رمز کلید را در محل امن نگهداری کنید.
  • فایل Keystore را در مخزن عمومی Git قرار ندهید.
  • آن را برای دیگران ارسال نکنید.
  • فایل را حذف یا با Keystore جدید جایگزین نکنید.

اگر نسخه های بعدی را با کلید متفاوت امضا کنید، Android معمولا اجازه نصب آن نسخه به عنوان به روزرسانی روی نسخه قبلی را نمی دهد. حفظ کلید اولیه برای انتشار نسخه های بعدی اهمیت حیاتی دارد.

۷. دریافت SHA256 از گواهی امضا

برای تایید ارتباط بین اپلیکیشن اندروید و دامنه وب، به SHA256 گواهی امضا نیاز داریم.

ابتدا مسیر keytool.exe را پیدا کنید و سپس دستور زیر را اجرا کنید:

& "$env:USERPROFILE\.bubblewrap\jdk\jdk-17.0.11+9\bin\keytool.exe" -list -v -keystore ".\android.keystore" -alias android

مسیر Keystore و نام Alias را با مقادیر واقعی پروژه خود جایگزین کنید.

پس از وارد کردن رمز صحیح، خروجی شامل اطلاعات گواهی خواهد بود. خطی با عنوان زیر را پیدا کنید:

SHA256: AA:BB:CC:DD:...

مقدار SHA256 باید از خروجی واقعی keytool کپی شود؛ آن را دستی حدس نزنید یا تغییر ندهید.

فرمت صحیح Fingerprint

Fingerprint گواهی SHA-256 شامل ۳۲ بایت است که به صورت ۶۴ رقم هگزادسیمال و با جداکننده دونقطه نمایش داده می شود. کاراکترهای معتبر هگزادسیمال عبارت اند از:

0-9
A-F

بنابراین حروفی مانند R یا T در Fingerprint معتبر نیستند.

در فایل assetlinks.json خود مقدار Fingerprint را وارد کنید؛ پیشوند SHA256: نباید در مقدار JSON قرار بگیرد.

اگر keytool هشدار غیرمنتظره ای نشان داد، رمز و مسیر Keystore را دوباره بررسی کنید و مطمئن شوید اطلاعات گواهی به درستی خوانده شده است. صرفا به وجود یک خط خروجی اکتفا نکنید؛ Fingerprint باید متعلق به گواهی واقعی باشد.

۸. ساخت APK و خطاهای واقعی Build

پس از تکمیل تنظیمات پروژه، دستور Build را اجرا کنید:

bubblewrap build

این دستور پروژه اندروید را Build می کند و در صورت موفقیت، فایل APK امضا شده تولید می شود.

در این مسیر دو خطای مهم رخ داد.

خطای اول: دریافت نشدن فهرست Android SDK

در اجرای اولیه Build، Android SDK Manager نتوانست فهرست پکیج ها را دریافت کند. بخشی از خروجی چنین بود:

Failed to download any source lists
Failed to find package build-tools;36.1.0

این خطا لزوما به معنی اشتباه بودن کد پروژه نیست. ممکن است دریافت فهرست پکیج ها به دلیل اختلال شبکه، دسترسی نداشتن به مخزن یا مشکل SDK Manager انجام نشده باشد.

در این پروژه، پس از پذیرفتن License قدیمی Android SDK، دانلود و استخراج Build Tools انجام شد.

برای عیب یابی:

  1. اتصال شبکه و دسترسی به مخازن Android SDK را بررسی کنید.
  2. پیام دقیق SDK Manager را بخوانید.
  3. License های SDK را بررسی و در صورت نیاز تایید کنید.
  4. مطمئن شوید نسخه Build Tools مورد نیاز پروژه قابل دریافت است.
  5. بعد از نصب موفق ابزارها، Build را دوباره اجرا کنید.

پذیرفتن License به تنهایی تضمین نمی کند مشکل شبکه یا دانلود حل شود؛ نصب واقعی پکیج ها نیز باید موفق باشد.

خطای دوم: ناسازگاری minSdkVersion

پس از عبور از مرحله دریافت SDK، Build با این خطا متوقف شد:

uses-sdk:minSdkVersion 21 cannot be smaller than version 24 declared in library com.google.androidbrowserhelper:androidbrowserhelper:2.7.4

این خطا به ناسازگاری حداقل نسخه Android تعریف شده در اپلیکیشن با حداقل نسخه مورد نیاز یکی از کتابخانه های آن اشاره می کند.

کتابخانه زیر حداقل API Level برابر 24 را اعلام کرده بود:

com.google.androidbrowserhelper:androidbrowserhelper:2.7.4

در حالی که مقدار minSdkVersion پروژه 21 بود.

راه حل انتخاب شده، هماهنگ کردن حداقل نسخه پشتیبانی پروژه با نیاز کتابخانه بود. در فایل app/build.gradle مقدار را از 21 به 24 تغییر دهید:

defaultConfig {
    minSdkVersion 24
}

ساختار دقیق فایل ممکن است در نسخه های مختلف Gradle متفاوت باشد؛ مقدار موجود را در محل صحیح پروژه تغییر دهید.

از راه حل هایی مانند tools:overrideLibrary برای دور زدن این ناسازگاری استفاده نکنید، مگر اینکه سازگاری واقعی کتابخانه با نسخه های پایین تر را بررسی و اثبات کرده باشید. Override کردن صرفا برای عبور از Build ممکن است باعث خطای زمان اجرا شود.

پیامد این تغییر: اپلیکیشن روی نسخه های Android پایین تر از API Level 24 قابل نصب نخواهد بود. پیش از انتشار، این محدودیت را با جامعه کاربران هدف خود بسنجید.

زمان طولانی Build

ساخت پروژه اندروید ممکن است در اجرای اول زمان بر باشد؛ چون Gradle و Android SDK باید وابستگی ها و ابزارهای مورد نیاز را دریافت یا آماده کنند. در این تجربه، یک اجرای Build بیش از ۱۲ دقیقه طول کشید و در نهایت به دلیل خطای minSdkVersion متوقف شد.

طولانی شدن Build به تنهایی نشانه هنگ کردن نیست. خروجی ترمینال را بررسی کنید و تا زمانی که فرایند فعال است، از بستن آن خودداری کنید.

۹. فایل APK نهایی کدام است؟

پس از Build موفق، Bubblewrap فایل های خروجی را در پوشه پروژه تولید می کند.

برای انتشار مستقیم باید فایل امضا شده را انتخاب کنید:

app-release-signed.apk

فایل بدون امضا، مانند app-release-unsigned.apk، برای توزیع مستقیم به کاربران انتخاب مناسبی نیست.

می توانید فایل امضا شده را به نام ساده تری تغییر دهید:

faridkarami.apk

تغییر نام فایل APK، امضای دیجیتال یا شناسه بسته داخل آن را تغییر نمی دهد. پس از تغییر نام نیز فایل همان اپلیکیشن امضا شده باقی می ماند.

برای نمونه، می توانید آن را روی وب سایت در این مسیر قرار دهید:

https://app.faridkarami.ir/download/faridkarami.apk

یا از دامنه اصلی استفاده کنید:

https://faridkarami.ir/download/faridkarami.apk

نکات انتشار فایل APK

  • فقط APK امضا شده و نهایی را منتشر کنید.
  • پس از هر Build جدید، فایل قبلی را با نسخه جدید جایگزین کنید.
  • مطمئن شوید فایل از طریق HTTPS قابل دریافت است.
  • بهتر است سرور برای فایل APK این Content-Type را ارسال کند:
application/vnd.android.package-archive
  • پیش از اعلام لینک عمومی، دانلود و نصب فایل را روی یک دستگاه واقعی آزمایش کنید.
  • نسخه و شماره Build اپلیکیشن را مدیریت کنید تا کاربران بدانند چه نسخه ای نصب می کنند.

۱۰. تنظیم Digital Asset Links و فایل assetlinks.json

یکی از مهم ترین مراحل راه اندازی TWA، تایید ارتباط بین اپلیکیشن اندروید و دامنه وب است.

این ارتباط با Digital Asset Links برقرار می شود. فایل تایید باید در مسیر مشخصی روی همان دامنه ای قرار بگیرد که TWA از آن اجرا می شود.

برای پروژه FaridKarami:

https://app.faridkarami.ir/.well-known/assetlinks.json

ساختار فایل به شکل زیر است:

[
	{
		"relation": ["delegate_permission/common.handle_all_urls"],
		"target": {
			"namespace": "android_app",
			"package_name": "ir.faridkarami.app.twa",
			"sha256_cert_fingerprints": ["YOUR_REAL_SHA256_FINGERPRINT"]
		}
	}
]

مقادیر مهم:

فیلد مقدار یا توضیح

relation رابطه مجاز برای مدیریت لینک های دامنه namespace مقدار ثابت android_app package_name مقدار دقیق applicationId پروژه sha256_cert_fingerprints Fingerprint واقعی گواهی امضای اپلیکیشن

در این پروژه، applicationId برابر ir.faridkarami.app.twa بود؛ بنابراین package_name نیز باید همین مقدار باشد.

اشتباه رایج: استفاده از namespace اشتباه

ممکن است تصور کنید چون در Gradle مقدار زیر وجود دارد:

namespace "ir.faridkarami.app.twa"

پس باید همین مقدار را در فیلد namespace فایل assetlinks.json قرار دهید. این برداشت اشتباه است.

در Digital Asset Links، مقدار namespace باید android_app باشد و شناسه واقعی برنامه در فیلد package_name قرار می گیرد.

محل قرارگیری فایل

در سرور وب، فایل را در این مسیر قرار دهید:

.well-known/assetlinks.json

این فایل باید از آدرس زیر قابل دریافت باشد:

https://app.faridkarami.ir/.well-known/assetlinks.json

برای بررسی پاسخ سرور:

curl.exe -i https://app.faridkarami.ir/.well-known/assetlinks.json

مواردی که باید بررسی شوند:

  1. پاسخ HTTP موفق، ترجیحا 200 OK باشد.
  2. محتوای پاسخ JSON معتبر باشد.
  3. آدرس به صفحه دیگری Redirect نشود یا محتوای HTML برنگرداند.
  4. package_name دقیقا با applicationId یکسان باشد.
  5. Fingerprint دقیقا متعلق به گواهی امضای APK باشد.

تا زمانی که Fingerprint واقعی به دست نیامده است، فایل نمونه را منتشر نکنید.

۱۱. تفاوت گواهی امضای محلی و Google Play App Signing

اگر APK را مستقیما از وب سایت توزیع می کنید، Fingerprint گواهی ای که APK را با آن امضا کرده اید اهمیت دارد.

اما اگر اپلیکیشن را در Google Play منتشر کنید و قابلیت Play App Signing فعال باشد، ممکن است گواهی امضای APK دانلود شده از Google Play با گواهی Upload Key شما متفاوت باشد.

در این حالت، برای اینکه TWA در نسخه نصب شده از Google Play نیز دامنه را معتبر تشخیص دهد، باید Fingerprint گواهی App Signing مربوط به Google Play را هم در assetlinks.json قرار دهید.

اگر هم نسخه مستقیم سایت و هم نسخه Google Play را ارائه می کنید، ممکن است لازم باشد Fingerprint هر دو گواهی در آرایه sha256_cert_fingerprints قرار بگیرد.

بنابراین پیش از انتشار عمومی مشخص کنید APK با کدام کلید امضا شده و کاربران آن را از چه مسیری دریافت می کنند.

۱۲. چک لیست نهایی پیش از انتشار

  • وب اپلیکیشن https://app.faridkarami.ir روی موبایل به درستی کار می کند.
  • Web App Manifest معتبر و در دسترس است.
  • آیکون اصلی برنامه با کیفیت مناسب انتخاب شده است.
  • Monochrome Icon با فرمت و MIME type مناسب ارائه شده است.
  • شناسه applicationId نهایی و ثابت است.
  • مقدار minSdkVersion با نیاز کتابخانه های پروژه سازگار است.
  • Keystore و رمزهای آن در محل امن نگهداری می شوند.
  • فایل APK با موفقیت Build و امضا شده است.
  • Fingerprint واقعی SHA256 از گواهی امضا استخراج شده است.
  • فایل assetlinks.json در مسیر /.well-known/ قرار دارد.
  • package_name با applicationId مطابقت دارد.
  • namespace در assetlinks.json برابر android_app است.
  • فایل assetlinks.json با HTTP 200 و JSON معتبر پاسخ می دهد.
  • APK روی یک دستگاه واقعی نصب و اجرا شده است.
  • لینک دانلود مستقیم از بیرون محیط توسعه قابل دریافت است.

نتیجه گیری

با استفاده از TWA و Bubblewrap می توان برای یک وب اپلیکیشن آماده، نسخه اندرویدی ساخت؛ بدون اینکه لازم باشد رابط کاربری آن را از ابتدا با فناوری Native بازنویسی کنیم.

با این حال، ساخت APK تنها بخشی از کار است. آماده سازی آیکون ها، تنظیم شناسه بسته، انتخاب حداقل نسخه Android، نگهداری Keystore، امضای خروجی و پیکربندی Digital Asset Links همگی در اجرای صحیح و انتشار نسخه نهایی نقش دارند.

در تجربه ساخت اپلیکیشن FaridKarami، مهم ترین چالش ها شامل خطای MIME type برای آیکون ICO، مشکل دریافت Android SDK، ناسازگاری minSdkVersion با کتابخانه Android Browser Helper و تشخیص تفاوت namespace در Gradle با namespace در فایل Digital Asset Links بود.

در نهایت، خروجی مناسب برای توزیع مستقیم، فایل APK امضا شده است؛ فایلی که می توان آن را با نامی ساده مانند faridkarami.apk روی وب سایت قرار داد و از طریق یک لینک HTTPS در اختیار کاربران گذاشت.

توصیه پایانی: پیش از انتشار عمومی، نصب و اجرای نسخه نهایی را روی چند دستگاه واقعی آزمایش کنید و از Keystore نسخه پشتیبان امن داشته باشید. این دو اقدام از بسیاری از مشکلات انتشار و به روزرسانی آینده جلوگیری می کنند.
